# PRD — Personal Agentic Software Factory (v1)

## 1. Overview

A personal, single-repo pipeline that turns a tagged GitHub issue into a pull request with no human prompting a terminal. Herdr dispatches the issue to a coding agent configured with Gentle-AI; the agent does the work under ODD/SDD + RDD discipline; the factory opens a PR on success or comments on the issue on failure. This is a learning project — v1 optimizes for a trustworthy, observable loop, not throughput.

## 2. Goals (v1)

- One tagged issue → one PR, end to end, with no manual invocation.
- Global on/off switch, checked before any other logic runs.
- Bounded concurrency and a bounded daily volume, both configurable.
- No silent failures — every blocked or errored run is visible on the issue.

## 3. Non-Goals (v1)

- Auto-merge of any PR, regardless of size.
- Multi-repo operation (single repo now; config should make this swappable later without a rewrite).
- Reading or acting on PR review comments.
- Choosing *which* underlying agent runs a task — that selection logic belongs to Herdr/your custom skill, not this PRD.

## 4. End-to-End Workflow

1. Trigger (cron, script, or GitHub Action) runs on a schedule.
2. **Gate check:** if the factory is disabled, exit immediately.
3. **Capacity check:** count open issues currently labeled `factory-in-progress`. If at or above the concurrency limit, or the daily claim count is already at the daily limit, exit.
4. **Claim:** pick the oldest open issue labeled `dark-factory` with no `factory-in-progress` or `factory-blocked` label. Apply `factory-in-progress` immediately — this is the lock, and it must happen before any agent work starts.
5. **Execute:** invoke Herdr headless with the issue body/title as the task. Herdr dispatches to an agent; the agent runs under the Gentle-AI setup (ODD/SDD, RDD review) in an isolated worktree.
6. **On success:** open a PR from the worktree branch. PR description includes a GitHub closing keyword (`Closes #<issue>`) so merging the PR closes the issue. Remove `factory-in-progress`.
7. **On error or block:** post one comment on the issue explaining what happened and why it stopped. Replace `factory-in-progress` with `factory-blocked` so it isn't re-claimed automatically.
8. Loop ends; next trigger cycle repeats from step 2.

## 5. System Components

| Component | Responsibility |
| --- | --- |
| Trigger | Fires the cycle on a schedule; owns the gate and capacity checks |
| Label state | The only source of truth for what's claimed, in progress, or blocked |
| Dispatcher (Herdr) | Headless invocation, agent selection |
| Execution environment (Gentle-AI) | Memory, workflow discipline, and RDD review inside the run |
| Output handler | Opens the PR or posts the failure comment |
| Config | `enabled`, repo target, concurrency limit, daily limit, label names |

## 6. Label Lifecycle

- `dark-factory` — opt-in marker on an issue; input to the system, never removed by the factory.
- `factory-in-progress` — lock + concurrency counter. Applied right before work starts, removed on any terminal outcome (success or error).
- `factory-blocked` — terminal failure state. Issue is visible and not re-claimed; a human decides what happens next (fix and remove the label, or close it).

## 7. Configuration (example)

```yaml
enabled: true
repo: "fernando/<target-repo>"
concurrency_limit: 2
daily_limit: 2          # not specified yet — flagged as an assumption, see §9
labels:
  trigger: dark-factory
  in_progress: factory-in-progress
  blocked: factory-blocked
agent:
  dispatcher: herdr
  mode: headless
```

## 8. Functional Requirements

- **FR1** — The factory must check `enabled` before any other step and perform no action if false.
- **FR2** — The factory must not claim an issue if doing so would exceed `concurrency_limit` open `factory-in-progress` issues.
- **FR3** — The factory must not claim an issue if the day's claim count already equals `daily_limit` (UTC day boundary).
- **FR4** — The `factory-in-progress` label must be applied before the agent begins work, and removed on every exit path (success, error, crash recovery).
- **FR5** — No code path may merge a PR under any condition.
- **FR6** — Every error or blocked outcome must result in exactly one issue comment describing the failure.
- **FR7** — Repo target must be read from config, not hardcoded, even though only one repo is in scope for v1.

## 9. Open Questions / Risks

- **Daily limit value:** Can be modify by an user, so it needs to be configurable
- **Orphaned locks:** if a run crashes without reaching step 6/7, `factory-in-progress` never gets removed. v1 needs at least a manual unstick path (remove the label by hand); a timeout-based auto-release is a reasonable v1.1 addition. for now we're going to keep a manual removal of the label
- **Claimed vs. completed for the daily count:** recommend counting at claim time (step 4), since that's when the resource is actually consumed, not at completion.
- **Overlapping trigger runs:** if the trigger itself can run concurrently (e.g., two GitHub Actions runs overlapping), two cycles could race to claim the same issue. Simplest fix: make the trigger's own execution non-concurrent (e.g., a `concurrency` group in GitHub Actions) rather than building distributed locking.

## 10. Acceptance Criteria

- Setting `enabled: false` stops new claims within one trigger cycle, with zero side effects.
- An issue is never claimed while concurrency or daily limits are at capacity.
- A successful run always produces a PR that references and will close its issue.
- A failed run always produces exactly one explanatory comment and never retries itself.
- No merge ever happens without a human action.

## 11. Future Work (v2+, out of scope here)

Auto-merge for a narrow, structurally-defined "safe" diff class; multi-repo support; PR-comment-triggered revision runs (gated behind an explicit authorized trigger, not passive listening), automatically unstick path for Issues
